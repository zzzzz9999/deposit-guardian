# 租客卫士 — AI 使用实践文档

## 1. AI 在项目中承担的角色

本项目以 **Claude API** 为核心 AI 能力，覆盖三个场景：

| 场景 | AI 的作用 |
|------|---------|
| 实时对话咨询 | 扮演维权顾问，结合法律原文和实时搜索给出可操作建议 |
| 案例自动生成 | 从权威网页中提取、归类、结构化真实维权案例 |
| 法律文书生成 | 根据用户情况生成投诉信、律师函等文书草稿 |

## 2. 实践一：流式对话中的上下文工程

### 2.1 问题背景

直接让 Claude 回答租房法律问题，存在两个风险：
1. **幻觉法条**：引用不存在或不准确的法律条文
2. **信息滞后**：无法获取最新的政策变化和同类案例

### 2.2 解决方案：两层上下文注入

每次对话在发送给 Claude 之前，后端会自动构建两层上下文：

**第一层：法律原文注入（build_law_context）**

从用户消息中提取关键词，匹配本地法条库，将相关条文的完整原文和官方链接注入上下文。本地维护覆盖民法典租赁章节、消费者权益保护法、宪法等的完整原文，Claude 引用时直接取用，不自行生成。

**第二层：实时搜索注入（web_search_bing）**

```python
# 根据城市 + 平台 + 纠纷类型生成精准搜索词
query = build_search_query(city, platform, dispute_type)
# 例："蛋壳 租房押金纠纷 北京 法院判决 2025"

# Bing HTML 搜索，过滤低质内容源
results = search_bing(query, blocked_domains=["zhihu.com", "baidu.com", ...])
```

每次对话都执行搜索，搜索词根据用户消息智能生成，结果注入上下文并要求 Claude 优先引用。

**最终 messages 结构：**

```
system: [角色定义 + 5步引导流程 + 输出格式约束]
messages: [历史对话（最近 20 轮）]
最后一条 user: [原始消息 + 法律原文上下文 + 搜索结果上下文]
```

### 2.3 效果

- 引用的法律条文 100% 来自本地验证过的原文库，消除幻觉
- 每次回复都附带官方链接，用户可自行核实
- 搜索结果注入使回复能反映最新政策动态

## 3. 实践二：提示词工程

### 3.1 角色设定

避免将 AI 设定为"法律顾问"（可能引发合规风险），而是定义为：

> "温暖有力的租房权益顾问——像一个懂法律的朋友，先共情再给方案"

这一设定带来两个关键行为：
- **先共情**：收到用户消息后，先用一句话表达理解，再进入分析
- **给方案不给结论**：不说"你一定能赢"，而是说"你有这几步可以做"

### 3.2 结构化输出约束

系统提示词中明确要求输出格式：

```
输出要求：
1. 字数控制在 600 字以内
2. 使用 Markdown 格式（标题、列表、加粗）
3. 引用法律时必须：
   - 写明条文全称（如"《民法典》第713条"）
   - 附上完整原文
   - 附上官方链接
4. 行动步骤必须编号，每步不超过 2 句话
```

### 3.3 纠纷类型映射表

提示词中内置了 12 类纠纷到法律条文的映射，当用户描述某类问题时，AI 会优先引用对应法条：

| 纠纷类型 | 主要法律依据 |
|---------|------------|
| 自然损耗押金纠纷 | 《民法典》第713条 |
| 格式条款/合同陷阱 | 《民法典》第496条 |
| 押金与定金混淆 | 《民法典》第587条 |
| 恶意拖延不退 | 《民法典》第577条 |
| 违规涨租 | 《民法典》第720条 |
| 买卖不破租赁/强制驱逐 | 《民法典》第725条 |
| 房东擅自入室 | 《宪法》第39条 |
| 合同欺诈 | 《民法典》第148条、《消费者权益保护法》第8条 |

### 3.4 迭代过程中的关键调整

**问题 1：AI 回复过长，用户不耐烦**

初版没有字数限制，Claude 倾向于给出详尽的法律分析，导致回复动辄 1500 字。

解决：在提示词中加入"600 字以内"约束，并要求"行动步骤不超过 2 句话"。

**问题 2：AI 给出"建议咨询律师"的万能回复**

初版 Claude 在不确定时倾向于推卸给专业律师。

解决：在提示词中明确"你是用户能获得的第一道帮助，必须给出具体可操作的步骤，不能以'建议咨询律师'作为主要回答"。

**问题 3：法律引用没有来源，用户不信任**

解决：将"必须附官方链接"写入提示词约束，并通过法律原文注入机制在上下文中预置了链接，让 Claude 直接引用。

## 4. 实践三：AI 自动案例生成

### 4.1 任务设计

每日自动从权威来源抓取文章，交给 Claude 提取结构化案例。核心挑战：**一篇文章可能包含多个案例**，需要 Claude 自动识别并拆分。

数据来源（按优先级）：
- 最高人民法院官网典型案例（court.gov.cn）
- 住房和城乡建设部政策文件（mohurd.gov.cn）
- 国务院政策解读（gov.cn）
- DuckDuckGo HTML 搜索（替代 Bing，避开中文搜索被知乎劫持）

### 4.2 提取提示词设计

```
你是一个法律案例提取专家。
请从以下文章中提取所有租房纠纷案例，每个案例独立输出。

对每个案例，提取以下字段：
- title: 简洁的案例标题（20字以内）
- subtitle: 一句话背景
- description: 案例经过（150-300字，含纠纷起因、双方主张、判决结果）
- court_name: 审理法院
- court_reference: 案号
- verdict_year: 判决年份
- difficulty: easy|medium|hard
- success_rate: 租客胜诉概率（0-100）
- outcome: won|settled|lost|unclear|policy
- key_law: 适用法条
- is_rental_dispute: true|false

以 JSON 数组格式输出。如果没有租房纠纷案例，返回 []。

文章内容：{article_content}
```

### 4.3 质量控制

**去重机制**：对案例标题 + 来源 URL 做 SHA256，与数据库已有案例比对，避免重复入库。

**JSON 容错**：Claude 输出的 JSON 格式不稳定时，用正则提取数组或对象兜底，不直接丢弃。

**来源标注**：每条 AI 生成案例的描述末尾自动追加来源机构、文书编号、适用法条、原文链接，用户可追溯。

**人工兜底**：管理员可通过 `POST /api/admin/ai-cases/run` 手动触发，`GET /api/admin/ai-cases/status` 查看运行状态。

## 5. 工程实践总结

### 5.1 做对的事

**1. 法律原文本地化**

将法律原文维护在代码库中，而不是让 Claude 自己"记忆"法律内容。这是消除法律幻觉最有效的手段，也是用户信任度最重要的来源。

**2. 流式输出 + 搜索状态提示**

SSE 流式输出让用户感知到 AI 在"思考"，搜索状态文案（"正在搜索：蛋壳 租房押金纠纷…"）进一步降低等待焦虑。

**3. 提示词版本管理**

将系统提示词集中维护在 `prompts.py`，与业务逻辑解耦，便于回溯和迭代。

### 5.2 踩过的坑

**1. 搜索结果污染**

早期直接将 Bing 搜索结果注入上下文，导致 Claude 引用了知乎上不准确的"经验帖"。

解决：在 `web_search_bing()` 中添加域名黑名单，过滤知乎、百度等 UGC 平台，优先保留政府官网、法院官网的结果。

**2. 上下文窗口超限**

当对话轮数较多时，历史消息 + 法律原文 + 搜索结果可能超出上下文限制。

解决：对历史消息做滑动窗口截断（保留最近 20 轮），法律原文只注入与当前消息最相关的条文。

### 5.3 对类似项目的建议

1. **先做数据，再做 AI**：法律原文库、案例库是比提示词工程更重要的基础设施，数据质量决定 AI 输出质量上限。

2. **上下文注入优于微调**：对于垂直领域知识（法律条文、地方政策），上下文注入比微调更灵活、更易维护，且成本更低。

3. **结构化输出要有校验**：AI 生成的 JSON 不一定符合 schema，需要在应用层做字段校验和兜底处理。

4. **流式输出是用户体验的分水岭**：法律咨询场景下，用户愿意等待更长时间，但前提是能看到进度。
